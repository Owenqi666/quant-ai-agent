# v0.12 工程集成与升级边界

本轮完成范围沿用任务清单：数值正确性、提交恢复、执行阶段心跳、短写事务和终态读取。AI、RAG、真实行情适配、BRAIN、最终市场测试与整体 UI 重设计仍未接入。正式结果以发布目录的 `acceptance.json` 与 `runtime-upgrade.json` 为准。

## 请求与状态契约

- `POST /api/researches/{id}/revisions` 接受可选 `idempotency_key`。新前端在发送前保存原正文、原基础修订及请求键；回复丢失后重放原请求。相同键与正文确认原修订，改变正文返回冲突。已提交请求不受当前 latest revision 后续变化影响。
- `POST /api/regression-checks` 接受可选请求键和成对的 `expected_attempt_id` / `expected_result_digest`。摘要是完整保存的实验 state，区别于单个候选的审核摘要。新前端始终发送冻结目标；首次提交目标过期返回 412，重放成功收据确认原检查且不重新计算。
- schema 8 新增 `workflow_mutation_receipts`，业务记录与收据在同一事务提交。原 `mutation_receipts` 的历史行和列保持不变。旧调用可以省略请求键，此时没有幂等保证；不为历史操作编造收据。
- 问题创建和追加沿用已有后端请求去重，前端新增原请求持久保存。409 保留待确认请求供诊断；明确拒绝后才能解除请求并修改。
- `GET /api/runs/{id}/status` 只读数据库轻量状态，返回 `change_token`、当前 attempt、phase 和固定 `integrity_checked: false`。不读文件、不加载 engine state，也不声称检出了外部文件改写。
- 完整 `GET /api/runs/{id}` 使用同一 WAL 读快照返回详情与 `status_token`，仍完整检查结果。终态轻量 token 改变时重新读取详情；显式重新核验同时刷新图表。审核、回归、下载维持各自的完整校验入口。

## 发布与并发

任务领取先用短事务登记精确 attempt，再复制和校验输入。任何遗留目录都有持久 attempt 归属，复制后摘要不符则失败。准备、计算、核验和发布阶段持续心跳，取消与旧 worker 提交按精确 attempt 拒绝。

回归在 WAL 读快照中完成完整文件核验和独立参考计算，再用短写事务比较精确业务行、用例行及已验证文件的 stat/inventory，最后原子保存检查与收据。文件变化检测包含 inode、ctime、mtime、长度、类型和目录清单，属于本机普通并发修改防护，不是恶意文件系统认证。外部修改发生在提交之后时，后续完整核验仍负责检出。

相关算子语义升级为 v3，独立参考升级为 v4；不改写旧实验或给旧结果重新背书。精确边界算法和独立参考增加计算成本，原始测量与适用范围见 `v012_numerical.md`。claim 的并发 writer 等待缩短，而 claim 自身新增校验后变慢；不将此解释为全链路加速。

## 验收与上线顺序

1. 定向数值、幂等、迁移、文件漂移、真实进程中断和浏览器丢响应测试；各 Agent 独立目录保存证据。
2. 交叉审核后冻结源码，运行 `scripts/verify_release.py`，使用全新发布目录。通过才允许更新运行版本；不在验收期间修改源码。
3. 停止旧 launcher/API/worker；对原工作区离线备份，核对文件摘要、数据库完整性及历史业务行。
4. 先将备份恢复到新目录并用新源码包验证 schema 7→8、旧实验核验及收据恢复，再从同一已验收源码包启动原工作区。
5. 核对版本、schema、工作区身份、历史业务行、实验文件与前端资产，保存 `runtime-upgrade.json`。不创建人工审核或人工观测。

schema 8 不能直接由旧版本打开。若升级后需要回退，停止新服务，使用升级前备份恢复到新目录，再用保留的旧源码包启动；恢复目录的工作区身份会改变，旧浏览器本机草稿不会自动跨工作区应用。不能把设置中的 schema 数字手动改回 7。

所有测量仅针对本机合成数据工程工作负载。固定基线、独立参考、人工研究效用与真实投资表现是不同证据，不能互相替代。
