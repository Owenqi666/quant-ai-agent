# v0.7 评估、任务清单与 Agent 分工

起点：2026-10-01，本地 v0.6.0 / c7f5761，工作树干净。此前发布验收为 17 步、279 项 Python、62 项前端、14 项 Chrome E2E；这些是旧版本证据，本轮重新验收。

## 实施前评估

1. 已确认的恢复缺口：保存审核和批准回归用例每次创建新 ID，没有请求级幂等。服务已提交但客户端丢失响应时，再次提交可能重复。批准用例在 POST 成功后仍先等待目录刷新，刷新失败会保留可重复提交的表单。先补故障注入证据，再修复。
2. 已确认的使用限制：研究定义已有本机草稿机制，审核表单仍只使用组件内状态；离开或刷新会丢失未提交内容与计时。需要绑定工作区及冻结结果的显式恢复，未确认的请求不能变成一项新请求。
3. 维护性改进：App 同时维护工作区身份、研究选择、请求代次、实验轮询和视图。现有竞态测试已经通过；以提取独立 hooks 和保留行为为目标，不将重构视为新增业务能力。
4. 研究评价：Alpha101 已确认是用户研究材料，但目前没有实际人工判断和全流程耗时。准备可执行的人工对照协议与空白记录，不代填用户结论。
5. 外部条件：真实数据授权与时间规则、远端仓库目标尚未提供。本轮不修改这些边界，AI/RAG/BRAIN 继续预留，前端维持基础设计。

## 契约与边界

- ReviewCreate 和 CaseCreate 增加可选 idempotency_key，旧调用省略时保持原行为；新前端始终提供。服务器严格校验非空键和长度。
- 请求摘要包含操作种类、目标标识及规范化内容；同操作同 key 同请求返回首次记录，异请求返回 409。不同明确操作使用新 key，不能按内容合并用户有意提交的第二次审核。
- 首次业务写入与请求收据同一事务；回放不得追加业务记录/事件。重试返回原冻结目标，不能重新绑定到重试后的实验。
- 客户端在发送前保存固定请求及 key；未收到有效成功响应时保留“结果待确认”，安全重试原请求。成功保存与后续目录刷新独立处理。未确认请求不允许静默编辑成新请求。
- 草稿按工作区、run、candidate、attempt、result digest 隔离；提供恢复和丢弃选择，不在挂载时自动覆盖现有内容。过期目标不自动迁移。
- 仅保存明确结束的主动工作区间；刷新/离开造成的未结束区间标记中断，不将停机或离开时间计入人时。来源继续明确区分 human 与 automation。
- 存储不可用、草稿损坏、恢复版本不匹配必须可见；不能在无法持久化待确认请求时伪装为可跨刷新安全恢复。

## 执行顺序

1. 本文件先保存；隔离已验收 v0.6 预览，避免开发构建覆盖旧运行。
2. 三个独占范围并行实施；主线程准备对照协议、HTTP 故障恢复示例和集成。
3. 后端冻结后生成契约，接通前端；agent 交叉只读审查，由负责人修复。
4. 冻结源码，使用新的 release-v07-* 目录统一验收。失败保留原目录，修复后另建目录。
5. 本地 commit/tag；停旧服务、备份、恢复到新工作区再升级 schema，逐条核验历史实验后更新预览。
6. 最终任务状态与实际测试计数保存到交付目录，不改写冻结时的计划或旧结果。

## 集成复核决定

- 所有新界面审核均提供顶层 `expected_attempt_id` / `expected_result_digest`，包括未填写五维评估的通用审核。首次目标过期返回 412；原请求回放仍返回首次成功记录。旧接口仅使用分项审核目标时保留原有 409 行为。
- 成功响应后先删除原冻结目标的草稿，再确认删除待确认请求。任一步失败保留原请求键，防止崩溃后从旧草稿创建重复记录。浏览器故障注入覆盖此顺序。
- 原操作的确认入口独立于新审核资格。实验进入重试或当前产物不可审核时，仍允许确认先前的待确认请求；新增审核继续受当前完整性校验限制。
- 服务已提交后真实断开 HTTP 响应，随后同键并发重试与备份恢复重放均纳入统一验收。改变正文返回 409，失败预检不占请求键。
- 开发阶段测试失败保留在各 agent 的 development 目录；已修复测试目标字段、断言时序及选择器问题。最终发布证据以新的 release-v07-* 统一验收为准。
- 人工对照协议与模板保持待执行；不从自动化验收生成真实人工判断、人工效率或金融收益结论。
