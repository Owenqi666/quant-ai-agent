# v0.7 审核草稿与安全提交恢复

本功能面向本机单用户研究工作台，不引入 AI 判断。审核人的身份、来源和结论仍为声明；自动验收记录必须选择 `automation`。

## 用户操作

1. 在“审核与回归”中选择实验及候选。编辑过的审核会保存为浏览器本机草稿，包括通用判断、理由、声明来源、五项判断、审核人和已结束的主动工作区间。
2. 再次打开同一冻结结果时，系统提示“恢复审核草稿”或“丢弃审核草稿”。既有内容不会自动覆盖当前表单。候选、实验尝试、结果摘要或工作区改变时，不自动迁移旧草稿。
3. 如果离开时仍在计时，只保留“计时中断”标记。恢复后该未结束区间被排除，必须再次手动开始。明确结束的区间保留，停机时间不会变成人工工作时间。
4. 保存前，系统先把完整请求与唯一请求标识写入本机存储并回读确认，再发送 POST。审核和批准回归用例都采用此流程。
5. 网络断开、响应无法读取或契约验证失败时，显示“结果待确认”。服务器可能已经保存。原请求内容被锁定，使用“安全重试审核提交”或“安全重试回归批准”即可确认原结果，刷新页面后仍使用同一标识。
6. 即使当前实验进入新的尝试、仍在运行或校验未通过，原请求恢复入口仍保留。此时新审核独立禁用；回放只确认原历史记录，不视为当前产物通过校验。
7. 成功 POST 与列表刷新分别处理。保存成功即清空已提交内容；刷新失败会明确显示“已保存，列表刷新暂未成功”，不会把保存操作重新视为未提交。

## 状态及存储边界

- 草稿键由 workspace、run、candidate、attempt、result digest 构成，采用 JSON 数组编码，避免分隔符碰撞。请求键按工作区、操作及目标实验隔离。
- 新界面所有审核（包含未勾选分项的通用审核）都提交期望的 attempt 和 result digest；首次保存前由后端核对。分项审核保留同一目标的内部绑定。旧 API 调用省略顶层目标时保持历史兼容行为。
- 已发出的未知请求不能当普通草稿丢弃后换一个新键。HTTP 409 也保留原请求用于诊断；仅收到符合响应契约的明确非 409 客户端拒绝时，允许解除拒绝记录并重新编辑。其中新顶层目标过期会返回 412，表示此次未提交，可以解除后重新读取目标。
- 浏览器无法持久保存待确认请求时，阻止此项 POST，显示具体错误；不会宣称存在可跨刷新恢复的请求。其他页面可继续使用。
- 损坏或不匹配的待确认请求不会被覆盖，并阻止同范围新请求；损坏草稿可明确丢弃。需要保留证据时，先另行复制浏览器存储记录。
- 成功响应后先删除原冻结目标的草稿，再删除待确认请求；两步之间发生崩溃会保留原键以供安全重放。任何一步删除失败都会保留原请求，重复确认仍使用原键。成功回放返回原保存结果，不表示当前运行产物重新通过了完整性校验。
- 本机存储不是服务端备份；主动清除站点数据、换浏览器或隐私模式关闭窗口后，恢复信息可能丢失。没有跨设备草稿同步。每次独立提交生成新键，有意的第二次审核不会被按内容合并。
- 草稿不提供多标签页编辑合并；同一份审核以一个编辑窗口为操作边界。服务端幂等约束针对同一个请求标识，不把不同标识的两次明确操作按内容合并。
- 尚未发送的批准理由仍是当前表单内容；本轮仅要求审核完整草稿恢复，以及两种操作已发送请求的持久恢复。

## 可检查的验收

`frontend/src/reviewRecovery.test.ts` 检查完整目标隔离、显式区间保存、错误格式、固定请求不可替换、存储拒绝和静默丢写。`frontend/e2e/recovery.spec.ts` 在独立临时工作区和独占端口启动真实 API/worker，不使用 8765：

- 让真实审核 POST、批准 POST 完成落库，再故意丢失客户端响应；刷新页面并安全重试，确认请求体及请求标识相同，服务器记录各只有一条。
- 批准成功回放后注入目录刷新失败，确认界面仍承认已保存并清空表单。
- 检查理由、未知/失败判断、来源、已结束时间区间的显式恢复，以及中断计时排除、候选与结果摘要隔离。
- 真实首次审核落库后丢响应，拦截后续 GET 将界面所见实验模拟为新尝试且未验证；重载仍能回放原请求，新审核始终不可提交。这项浏览器场景只模拟读取状态，后端改变真实尝试的回放另由后端测试覆盖。
- 注入浏览器存储失败，确认提示可见且没有发出审核 POST。另注入已落库后的草稿删除失败，检查刷新后仍保留原键，恢复存储后重放只确认原记录。

实际执行结果记录在本轮验收产物中；这些自动化场景不构成人工语义评测或研究耗时改善证据。
