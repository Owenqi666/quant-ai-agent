# v0.12 客户端提交恢复与终态读取

## 新增覆盖

修订、问题创建、问题处理事件、回归检查现在与已有审核/批准/报告采用相同的持久原请求机制：先在浏览器确认保存，再发送；成功但响应丢失时保留原正文、目标与幂等键，刷新后可以确认原操作。

- 修订恢复区常驻研究页面，按工作区与研究隔离，不依赖仍选着原 base revision。成功确认只清理与提交时字节完全相同的原草稿；更新过的草稿保留。
- 问题创建按工作区与研究保存。问题处理请求另行保存，其原 issue 路径与 `base_event_id` 一并冻结；刷新后尚未选择 issue 时仍可恢复。
- 回归检查按工作区、研究与 run 保存，固定 case 集合及后端 `regression_target` 提供的 attempt 和完整 state digest，不从前端自行计算身份。
- 未确认或明确拒绝的请求禁止被当前编辑内容替换。明确拒绝可以解除，409 保持原请求供重放/诊断，不因冲突自动生成新键。
- 浏览器存储不可用时不发送。较晚完成的旧组件不改写新工作区，不清除新草稿；离开后仍未确认的请求在原作用域保留。

主要入口：`RevisionSubmission.tsx`、`FeedbackPanel.tsx`、`QualityPanel.tsx`，共用 `useRecoverableMutation.ts`、`MutationRecovery.tsx`。`taskRecovery.ts` 负责提交草稿的条件清理及恢复原 issue 路径。

## 终态实验读取

`useExperimentMonitor` 初次选择实验、显式刷新和显式重新核验仍读取完整结果。活动实验沿用完整轮询；终态实验每 5 秒请求轻量 `/runs/{id}/status`，仅当数据库 `change_token` 与上次详情 `status_token` 不同才重读完整结果。旧响应没有 token 时保守回退到完整读取。

轻量状态请求声明 `integrity_checked:false`。它不会发现文件系统中的独立篡改，不能作为文件完整性证明。页面显示上次完整加载的时间及该边界；“重新核验当前实验”重新加载结果、产物入口和候选图表。审核、回归与下载服务仍执行后端校验。

## 验证范围

`taskRecovery.test.ts` 覆盖原草稿/新草稿字节隔离、问题路由恢复、工作区隔离及损坏记录保留。

`client-recovery.spec.ts` 在独立临时工作区与 API/worker 上验证：

1. 修订提交成功后丢响应，刷新并重放原请求只返回原 revision，新草稿不被清除。
2. 问题创建和处理事件分别丢响应/刷新，原 issue ID 与事件只保存一次。
3. 旧工作区的延迟修订响应不能关闭或清理新工作区编辑器。
4. 回归检查在丢响应/刷新后使用原 attempt/state digest/case 集合，原 check 只出现一次。
5. 不变终态只轻量轮询；数据库变化引发详情更新；显式核验重新读取图表并拒绝已篡改产物。

既有导航延迟测试继续保留“返回同一研究仍不能被旧响应改变所选版本”的断言，并使用显式原请求确认，不再依赖卸载组件写入全局成功提示。

普通表单的未提交编辑、提交请求收据与真实研究结果是不同对象。上述验收记录全部为自动样例，不构成人工研究耗时或真实使用成果。
