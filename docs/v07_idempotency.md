# v0.7 审核与批准提交的安全重试

## 已确认的问题与修复

v0.6 中，相同审核或批准请求再次发送时都会生成新的业务 ID。提交已落库而客户端没有收到响应时，仅重试就可能产生重复记录。本轮在临时工作区复现了两次相同请求生成两条审核、两条批准；原始证据保留在 `artifacts/v07-idempotency-development/before-duplicate.json`。这份修复前证据属于服务级重复调用，真实网络丢响应由独立 HTTP 和浏览器验收覆盖。

现在客户端可以为一次明确操作提供固定 `idempotency_key`。首次成功提交的业务记录、审核事件和请求收据在一个 SQLite `BEGIN IMMEDIATE` 事务内写入。响应丢失时，原请求和原键返回首次成功记录，不会追加业务记录或审核事件。

## HTTP 契约

适用接口：

- `POST /api/runs/{run_id}/reviews`
- `POST /api/regression-cases`

两个 JSON 请求均新增可选 `idempotency_key: string | null`，默认 `null`。提供键时长度为 1 至 128 个字符，不能是空白字符串；服务器保留键原文。前端使用 UUID，并在发送前持久化键和完整请求。

审核请求另有一组可选顶层字段 `expected_attempt_id` 和 `expected_result_digest`，从运行详情的 `review_targets` 取得。两者须同时提供或同时为 `null`：attempt 为 1 至 64 字符的非空白字符串，digest 为 64 位小写十六进制。新前端对普通审核和结构化审核都提供这组字段；普通审核不需要编造 `assessment`。

首次提交时，服务在写事务内将这组字段与当前候选结果比较，不匹配返回 412（Precondition Failed），避免表单打开期间实验重试导致审核错绑新结果。412 明确表示该首次写入未提交，可将其与请求键冲突的 409 区分。字段缺一或格式非法返回 422。若请求同时含有结构化 assessment，顶层字段须与 assessment 内部目标一致，否则返回 422。旧调用可以继续省略顶层字段；仅含 assessment 的旧目标失配仍返回 409。

| 场景 | 行为 |
|---|---|
| 首次有效键和请求 | 创建业务记录及收据，返回原有响应结构和 201 |
| 同操作、同键、同规范化请求 | 返回首次响应和 201，不追加记录或事件 |
| 同操作、同键、不同有效请求内容或目标 | 409，不创建新记录 |
| 尚无成功收据且顶层目标与当前已验证候选不符 | 412，首次写入未提交，不预留键 |
| 不同键、相同内容 | 视为用户明确的新操作，按当前校验规则创建记录 |
| 省略键或显式 `null` | 保持旧接口行为，每次调用独立创建记录 |
| 非法键或无效请求输入 | 422，不预留键 |
| 首次业务验证失败或事务失败 | 不写入收据；后续可以使用同键重试有效请求 |
| 收据数据损坏或校验不匹配 | 409，不返回伪成功，也不生成替代记录 |

审核与批准的键分别属于 `review.create` 和 `case.approve` 命名空间。键在同一工作区内对该操作有效，包含所有研究和实验；将审核同键改用于另一实验会冲突。

请求摘要包含操作、目标标识和填入默认值后的结构化内容。JSON 对象键顺序不影响摘要；省略默认 `source` / `assessment` 与明确传入相同默认值一致。用户文字、空格、数组顺序、时间字符串保持原文，不把表达相似的研究判断自动合并。

明确提供的顶层审核目标也参与请求摘要，同键改目标返回 409。省略或显式传入两个 `null` 沿用未提供顶层目标时的摘要格式，保持已有收据兼容。字段对当前结果的比较发生在收据回放之后，已提交的旧目标请求仍可确认原提交。

客户端不能把所有 409 都当作可丢弃请求：它还可能表示键已用于其他内容，或当前产物无法重新验证。只有明确的成功响应确认原提交，或首次目标检查的 412 明确确认本次目标已过期；超时、断网等没有有效响应的请求仍应保留原键和请求进行确认。

## 原结果回放与完整性边界

收据查找发生在当前实验状态、结果目标和产物完整性校验之前。因此实验后来重试、处于排队状态或产物被篡改时，已成功的原请求仍可以确认原来的审核或批准。回放中的 attempt、result digest 和批准 contract 均取首次冻结响应，不会绑定到最新实验结果。

回放只确认过去成功提交的操作，不证明当前产物仍通过完整性校验。新的键仍必须通过现有完整性检查；结构化审核的旧目标不会自动转移。工作台的运行详情与回归检查继续负责当前完整性和数值验证。

收据保存响应 JSON、响应摘要和带外键的业务 ID。该摘要用于发现意外损坏，不是认证或防恶意数据库管理员篡改的签名。身份、人工来源以及语义判断继续遵守现有声明式边界。

## 迁移和恢复

数据库版本升级至 5，新增 `mutation_receipts` 表。迁移不改写旧审核、旧批准，也不为旧记录编造请求键。迁移 DDL、版本号和历史记录在一个事务内更新；失败回滚后可以重试。

备份支持 schema 1 至 5。收据随数据库完整备份；恢复到新路径后，相同请求仍返回原业务记录。收据不依赖原工作区文件路径。旧工作区应保持原样，通过离线备份恢复到新目录后升级。

## 验证范围

`tests/test_mutation_idempotency.py` 覆盖 HTTP 响应一致性、并发同键请求、内容和目标冲突、新键明确操作、旧调用及默认值兼容、非法键、收据插入后的事务回滚、首次目标校验失败、产物篡改后确认原提交、实验重试后的原目标回放、备份恢复与损坏收据拒绝。`tests/test_migrations.py` 增加 schema 4 至 5 原子升级和历史记录保留。

交叉复核后新增普通审核精确目标绑定的测试：旧表单首次提交拒绝错绑、新键仍校验旧目标、同键改目标冲突、结构化与顶层目标一致性、两个字段成对输入、实验重试后原请求回放。

这些是合成数据工程验证，不是人工研究效率或投资表现测量。正式验收的实际计数、完整 HTTP 故障注入和浏览器结果由对应发布目录记录。
