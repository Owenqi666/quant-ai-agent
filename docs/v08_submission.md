# v0.8 研究创建与实验提交契约

## 研究创建

`POST /api/researches` 接受可选 `idempotency_key`。键必须是包含非空白字符的字符串，长度为 1–128；省略或 `null` 保留旧调用行为，每次成功调用仍新建研究。明确发起新操作时应使用新键。

带键调用把 `research.create`、标题、论文 ID、数据集 ID 和原始任务正文组成规范 JSON 指纹。JSON 对象的字段顺序不影响指纹；用户文本、数组顺序和提交值保持原样，不用任务归一化结果代替原始意图。同键同正文返回第一次成功提交的研究详情，包括当时唯一的初始修订、`latest_revision_id` 和预检结果。后续新增修订不会改变这个创建确认；读取当前状态应使用研究详情 GET 接口。

研究、初始修订和响应收据在同一个 SQLite immediate transaction 中落库。同键并发只会有一个创建操作。任务校验、响应构建、收据写入或提交失败时不保留研究、不保留孤立修订，也不占用请求键。收据确认在当前任务重新校验之前执行，因此后来修改任务验证规则不会把原创建确认改成新创建。

相同键用于不同请求返回 409。收据响应摘要或资源标识不匹配也返回 409，并保留原记录供诊断，不创建替代研究。成功回放仍为 201，返回现有 ResearchDetail 结构，不新增一套响应包装。

收据只确认原操作已提交，不保证研究当前修订、数据文件和论文文件仍处于原来的状态，也不代替实验产物核验。浏览器应保存固定请求与键，继续确认同一操作；不能在响应不确定时自动换键。

## 实验提交

`POST /api/runs` 沿用既有必填键与数据库唯一约束，同键相同修订和执行模式确认同一 run，不追加 queued 事件。返回值仍是该 run 的当前 RunSummary：例如第一次响应为 queued，之后确认时可以是 completed、failed 或 cancelled。这是状态查询式确认，不将历史运行状态冻结成创建时的 queued。

研究创建与运行提交使用独立键命名空间。审核、批准仍各自使用已有 `review.create` / `case.approve` 命名空间，目标前置校验和原响应回放语义保持不变。

## Schema 6、历史和恢复

schema 5→6 在一个迁移事务中完成两项变更：

1. 扩展 `mutation_receipts`，增加研究外键及 `research.create` 约束。由于 SQLite 不能直接扩展原 CHECK，迁移重建此表并逐列复制旧行，原 `response` 字符串及其摘要保持原值；不重新序列化旧收据。
2. 建立 `research_reports` 及索引，供研究分析模块保存冻结快照。

任一项 DDL 失败，两项变更及迁移版本记录一起回滚。旧数据库按原迁移顺序逐级升级；历史研究、审核和批准不会补造请求键或收据，旧研究也不会补造总结。备份支持 schema 1–6，恢复会保留收据和报告内容；客户端尚未确认的请求仍由浏览器自己的存储持有，不混入服务器备份。

## 验证范围

实施前的 `artifacts/v08-submission-development/before-duplicate.json` 记录 v0.7 对同一创建参数连续调用两次 service 的结果：两个不同研究 ID。此证据只复现 service 级重复创建风险，没有声称进行了 HTTP 丢响应故障注入。

定向测试覆盖并发同键、旧调用兼容、异正文冲突、键校验、任务和事务失败回滚、后续修订后的原始响应回放、损坏收据拒绝、schema 5 迁移原文保留、迁移故障回滚、备份恢复，以及运行确认继续返回当前状态。真实 HTTP 响应丢失与浏览器刷新恢复由主线程统一验收记录提供；实际执行结果以对应产物中的日志为准。
